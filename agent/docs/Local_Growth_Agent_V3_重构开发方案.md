# Local Growth Agent V3 重构开发方案

更新时间：2026-09-15

## 1. 产品重新定义

Local Growth Agent 不是日报生成器，而是一个有历史记忆的本地推投放决策 Agent。

核心目标：

```text
每天 09:00 启动已登录浏览器下载脚本
    → 下载昨日报表并校验文件
    → 标准化并校验数据
    → 更新账户、计划、素材历史状态
    → 识别异常和状态变化
    → 诊断异常根因
    → 生成带优先级的具体动作
    → 推送日报
    → 写入石墨文档（具备权限时）
    → 读取执行反馈，进入下一天诊断上下文
```

日报是输出载体，石墨是协作界面，诊断和动作决策是核心价值。


## 3. 产品边界

### 3.1 V1 必须完成

- 每天 09:00 自动触发任务；
- 通过已登录浏览器自动下载账户核心投放报表；
- 支持账户、计划/单元、素材、线索反馈数据；
- 自动计算 CTR、CPC、留资转化率、单个留资成本、有效留资成本、对接成本和 CPM 等指标；
- 自动生成账户、计划、素材的历史序列；
- 判断计划和素材的当前阶段；
- 检测异常并给出根因候选；
- 输出带优先级的开关计划、预算和素材调整建议；
- 推送日报；
- 写入石墨文档指定位置；
- 读取上一日建议执行情况。

### 3.2 V1 给出建议 

系统负责分析并建议：

- 暂停、保留或观察计划；
- 增加或降低预算；
- 调整出价；
- 替换或重做素材；
- 检查表单、承接、回传和跟进。

### 3.3 后续扩展

- 从石墨文档识别线索并生成标签建议；
- 通过抖音来客接口执行标签写入；
- 运营执行结果自动回写；
- 计划预算或状态的半自动执行；
- 飞书、企业微信等其他推送渠道。

## 4. 系统分层

```text
┌──────────────────────────────────────┐
│ Scheduler / 09:00 定时任务            │
└──────────────────┬───────────────────┘
                   ↓
┌──────────────────────────────────────┐
│ Skill：取数、字段映射、指标计算、写入 │
└──────────────────┬───────────────────┘
                   ↓
┌──────────────────────────────────────┐
│ State Store：账户/计划/素材历史状态   │
└──────────────────┬───────────────────┘
                   ↓
┌──────────────────────────────────────┐
│ Rule Engine：基线、窗口、异常检测      │
└──────────────────┬───────────────────┘
                   ↓
┌──────────────────────────────────────┐
│ Agent：根因诊断、建议排序、动作生成    │
└──────────────────┬───────────────────┘
                   ↓
┌──────────────────────────────────────┐
│ Push / Graphite：推送与协作记录        │
└──────────────────┬───────────────────┘
                   ↓
┌──────────────────────────────────────┐
│ Feedback：执行结果和次日上下文        │
└──────────────────────────────────────┘
```

原则：

- Skill 负责确定性工作；
- Rule Engine 负责计算、比较和触发异常；
- Agent 负责解释、归因、处理冲突和生成动作；
- 石墨负责展示和人工反馈；
- 所有外部接口都通过适配器隔离，不能把 API 细节写死在诊断逻辑中。

## 5. Skill 设计

### 5.1 `report_download_skill`

职责：

- 使用已登录浏览器进入本地推报表页面；
- 选择昨日或当月 1 日至昨日的统计范围；
- 下载账户、计划、素材报表；
- 记录下载时间、数据日期、账户 ID、页面和原始文件路径；
- 校验下载完成、文件大小和统计日期；
- 下载失败时输出明确错误，不生成假日报。

输出：

```json
{
  "account_id": "...",
  "data_date": "2026-09-13",
  "fetched_at": "2026-09-14T09:00:00+08:00",
  "sources": ["browser_export_account", "browser_export_plan", "browser_export_material", "lead_feedback"],
  "status": "success",
  "raw_records": 0,
  "errors": []
}
```

### 5.2 `metrics_skill`

职责：

- 统一字段名和数据类型；
- 计算基础指标；
- 保留原始值和计算值；
- 分母为 0 时输出 `null`，不能输出虚假的 0；
- 对不同数据源进行总量核对。

至少支持：

- CTR = 点击 / 展示；
- CPC = 消耗 / 点击；
- 留资转化率 = 留资 / 点击；
- 单个留资成本 = 消耗 / 留资；
- CPM = 消耗 / 展示 × 1000；
- 有效留资成本 = 消耗 / 有效留资；
- 对接成本 = 消耗 / 对接数量。

### 5.3 `daily_report_skill`

职责：

- 组装基础日报数据；
- 按模板生成日报；
- 写入石墨指定位置；
- 推送日报正文和异常摘要；
- 返回写入位置、文档版本和任务状态。

日报不负责自行判断根因。根因和动作由 Agent 输出后，由 Skill 负责排版和写入。

### 5.4 `graphite_skill`

职责：

- 定位石墨文档和指定章节；
- 新建日期小节或更新当天小节；
- 写入基础数据、诊断、建议和反馈区；
- 支持幂等更新，避免 09:00 任务重试造成重复日报；
- 记录写入失败原因。

## 6. 数据模型

### 6.1 原始数据层

保存接口原始返回，不覆盖、不删除，用于追溯。

### 6.2 标准化数据层

#### `account_daily`

```text
date, account_id, spend, impressions, clicks, leads,
valid_leads, private_messages, contacted_leads
```

#### `plan_daily`

```text
date, account_id, plan_id, plan_name, campaign_type,
bid_strategy, bid, budget, status, spend, impressions,
clicks, leads, valid_leads, private_messages, contacted_leads
```

#### `material_daily`

```text
date, account_id, plan_id, material_id, material_name,
material_type, spend, impressions, clicks, leads,
valid_leads, private_messages, contacted_leads, reject_reason
```

#### `lead_feedback`

```text
lead_id, lead_date, account_id, plan_id, material_id,
is_valid, screened_at, is_contacted, contacted_at, phone_connected, wechat_added,
first_response_minutes, appointment, deal, revenue,
feedback_date, invalid_reason
```

### 6.3 状态层

#### `plan_state`

```text
plan_id
first_seen_date
last_seen_date
last_spend_date
active_days
current_stage
recent_3d_metrics
baseline_7d_metrics
baseline_30d_metrics
observed_status
last_recommendation
last_action_feedback
```

#### `material_state`

```text
material_id
first_seen_date
last_spend_date
active_days
current_stage
recent_3d_metrics
historical_best_metrics
fatigue_signals
last_recommendation
```

`observed_status` 必须区分：

- `spending`：当天有消耗；
- `no_spend`：记录存在但当天无消耗；
- `not_observed`：当天没有该对象记录；
- `unknown`：数据拉取不完整，不能判断。

不能把“无消耗”直接写成“后台已暂停”。

## 7. 基线和阶段模型

### 7.1 账户基线

每次诊断前自动装配：

- 近 7 日 CTR、留资转化率、单个留资成本、有效留资成本的均值和中位数；
- 近 30 日中位数和波动范围；
- 按通投/搜索拆分的基线；
- 按计划阶段拆分的基线；
- 数据完整天数和样本量。

第一版优先使用中位数、近 3 日和近 7 日窗口，标准差只作为辅助，不把单一标准差阈值当成绝对规则。

### 7.2 计划阶段

```text
未观察
    → 冷启动
    → 测试
    → 成长
    → 稳定
    → 衰退
    → 休眠/停止观察
```

阶段判断需要同时参考：

- 有效投放天数；
- 累计样本；
- 最近 3 日变化；
- 最近一次稳定窗口；
- 消耗承接能力；
- CTR、留资转化率、有效留资成本；
- 是否有预算、出价、时段或计划状态变更。

### 7.3 素材阶段

```text
新素材 → 验证中 → 有效 → 稳定 → 衰减 → 替换
```

素材衰减至少要区分：

- 点击层衰减：CTR下降；
- 留资层衰减：留资转化率下降；
- 质量层衰减：有效留资率下降或有效留资成本上升；
- 供给层衰减：预算未变但消耗承接下降；
- 结构性问题：预算、出价、时段、审核或计划开关变化。

## 8. 异常检测与根因诊断

### 8.1 Rule Engine 先发现异常

规则引擎只负责回答：

```text
是否异常？
异常发生在哪一层？
样本是否足够？
是否需要 Agent 进一步解释？
```

至少检测：

- CTR、CPC、留资转化率、单个留资成本、有效留资成本和对接成本的近期变化；
- 消耗突然上升或下降；
- 计划连续无消耗；
- 计划频繁开关；
- 高消耗无留资、无有效留资或无对接；
- 素材进入衰减信号；
- 单元表和素材表总量不一致；
- 数据拉取不完整；
- 新旧计划预算结构异常。

### 8.2 根因诊断顺序

以 CTR 下降为例：

```text
CTR下降
  ↓
确认展示、点击和日期数据完整
  ↓
检查预算、出价、时段、计划状态是否变化
  ↓
检查素材有效投放天数、频次和近期历史
  ↓
检查同账户或同人群计划是否重叠
  ↓
检查通投/搜索、素材类型和人群分层
  ↓
输出根因候选、证据和置信范围
```

根因分类：

- `creative_fatigue`：素材疲劳；
- `audience_overlap`：受众或计划重叠；
- `bid_or_budget`：出价、预算、时段变化；
- `delivery_change`：平台分配或供给变化；
- `funnel_mismatch`：素材承诺与表单/产品承接不匹配；
- `tracking_issue`：转化或回传异常；
- `insufficient_sample`：样本不足，不能归因。

Agent 不允许只看到 CTR 下降就直接断定“素材疲劳”。必须先排除数据、预算、出价、时段和计划状态变化。

### 8.3 根因输出格式

```text
异常：计划 A 近3日 CTR 下降 27%。

主要根因：暂偏向素材疲劳，但不是确定结论。

证据：
- 预算、出价和投放时段未发现明显变化；
- 计划已连续有效投放 8 天；
- 同一素材近期展示增加，但点击率连续下降；
- 同账户其他计划 CTR 没有同步下降。

需要排除：
- 是否存在同人群计划重叠；
- 是否发生素材审核或投放限制；
- 当前频次是否明显高于历史正常水平。
```

## 9. 动作建议引擎

### 9.1 建议必须包含

- 优先级：P0、P1、P2；
- 对象：账户、计划或素材；
- 动作：开启、暂停、降预算、加预算、替换素材、检查回传等；
- 幅度：百分比或预算区间；
- 数据依据；
- 预期目的；
- 复盘时间；
- 是否需要人工确认。

### 9.2 标准动作类型

```text
HOLD
MINOR_ADJUST
CONTROL_RISK
STOP_OR_REPLACE
SCALE
CHECK_DATA
CHECK_FOLLOW_UP
```

### 9.3 放量条件

放量建议必须同时满足：

- 最近 3 日有持续留资或有效留资；
- 有效留资成本达到业务目标或低于账户基线；
- 有效留资率、对接率和可触达质量没有明显恶化；
- CTR/留资转化率没有连续恶化；
- 没有明显素材疲劳或合规风险。

放量动作默认按10%–20%递增，放量后至少观察24小时，正式复盘使用2–3天窗口。

### 9.4 关停条件

关停建议需要满足以下至少一项，并检查样本量：

- 消耗达到目标有效留资成本的1.5–2倍，仍无有效留资；
- 连续2–3天无留资或无有效留资，且成本持续恶化；
- 有效留资率或对接率低于业务最低线；
- 明确的数据、审核或合规风险；
- 计划已经进入衰退且新素材已有替代样本。

数据不足时，输出 `HOLD` 或 `CHECK_DATA`，不能为了给出动作而强行关停。

## 10. Agent 运行流程

### 10.1 每日任务

```text
09:00 触发任务
  ↓
读取账户配置和昨日执行反馈
  ↓
启动浏览器下载脚本，取得昨日导出文件
  ↓
校验数据完整性和总量
  ↓
写入原始层和标准化层
  ↓
更新计划、素材状态
  ↓
计算账户基线和近期窗口
  ↓
运行异常检测
  ↓
对异常调用 Agent 根因诊断
  ↓
生成优先级建议
  ↓
组装基础日报和诊断日报
  ↓
推送日报
  ↓
写入石墨
  ↓
记录任务日志和版本
```

### 10.2 Agent 输入上下文

每次诊断只装配相关上下文：

- 当前异常记录；
- 对象近3日、近7日、近30日指标；
- 对象历史最佳和最近稳定窗口；
- 账户基线；
- 同层级对照对象；
- 预算、出价、时段、状态变更；
- 昨日建议及执行反馈；
- 数据质量警告。

不要把整个账户全部原始数据无差别塞给 LLM。

## 12. 反馈闭环

石墨日报中保留人工反馈区，第一版允许人工填写：

```text
未执行
已执行
部分执行
判断不准确
继续观察
```

每条反馈至少记录：

- recommendation_id；
- 是否执行；
- 执行动作；
- 执行时间；
- 执行后 1 日和 3 日结果；
- 人工认为建议是否正确；
- 误判原因。

第二天 Agent 读取反馈，并在诊断中区分：

- 建议未执行，不能评价建议效果；
- 建议已执行，结果改善；
- 建议已执行，结果无改善；
- 建议执行方式与原建议不同。

## 13. 线索标签扩展

第一版只做：

- 读取石墨中的线索文本；
- 识别身份、年级、国家、求职阶段、意向方向等信息；
- 输出建议标签和待人工处理列表。

第一版不依赖抖音来客标签 API。只有当接口权限、字段和写入方式确认后，才进入自动写标签开发。

## 14. 直接实施清单

第一轮直接实现完整的每日运行链路，目标是每天 09:00 稳定完成：

```text
浏览器下载 → 文件校验 → 指标计算 → 日报生成 → 推送 → 石墨写入
```

基础链路验收：

- 任务可手动触发和定时触发；
- 同一天重复执行不产生重复日报；
- 下载失败或文件不完整时不生成错误日报；
- 日报可以追溯数据日期、拉取时间和数据源。

随后在同一条链路中接入状态和异常引擎，系统能维护：

- 每日计划投放轨迹；
- 素材有效投放天数；
- 近期3日、7日和历史基线；
- 计划/素材阶段；
- CTR、CPC、留资转化率、有效留资成本和消耗异常。

状态和异常验收：

- 能识别“当天有消耗”和“当天无消耗”；
- 能识别计划断量和频繁开关；
- 能区分样本不足和真实异常；
- 能识别类似 `8-28深转` 的历史有效、当前衰减状态。

再接入根因诊断和人工执行建议，Agent 对异常输出：

- 根因候选；
- 证据；
- 排除项；
- 优先级；
- 具体动作；
- 调整幅度；
- 复盘时间。

诊断和建议验收：

- 不把 CTR 下降直接等同于素材疲劳；
- 能区分点击层、留资层和质量层问题；
- 不把累计好数据误判为当前仍适合放量；
- 每条建议都能追溯到结构化数据。

最后接入反馈和线索标签建议：

- 读取石墨中的昨日执行反馈；
- 评估建议执行后的结果；
- 生成线索标签建议；
- 沉淀真实案例。

## 15. 第一批测试案例

第一批不使用抽象案例，直接使用账户真实历史数据构造：

1. `8-28深转`：累计表现好，但后期素材衰减；
2. `9.3素材6-10浅层`：留资不少，但有效留资率低；如果历史数据没有人工筛选字段，不得把其他质量字段自动等同于有效留资；
3. 9/5：有点击、有消耗、0线索；
4. 9/8：CTR尚可，但留资转化率明显下降；
5. 9/9后：计划逐步停止，账户断量；
6. 新计划样本不足，不能提前关停；
7. 预算或出价变化导致的假性素材异常；
8. 单元表和素材表口径不一致；
9. 建议已执行但数据未改善；
10. 建议未执行，不能评价效果。

## 17. 当前开发决策

- 当前主路线为浏览器自动下载文件；
- 保留 API 适配器作为未来可选路线，不阻塞当前开发；
- 新版以“状态、基线、根因、动作、反馈”为主线；
- 取数、状态、诊断、建议和反馈共用同一条每日运行链路；
- 线索标签不阻塞主链路；
- 下载失败、登录失效或文件不完整时不假装完成真实取数；
- 所有计划、预算、出价和素材调整只输出建议，由人工在后台执行；
- 不让 LLM承担指标计算、数据校验和后台执行。
